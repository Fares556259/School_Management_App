# Missing billing schema repair

Applied: 2026-11-22, through the SQL Editor of the production Supabase project already used by this application. This record describes a schema repair, not a successful payment acceptance test.

## Cause

The level-fee settings used existing Level/Institution data, but opening the collection window also queries StudentCharge, StudentChargeCategory and StudentServiceAssignment. Production had none of those tables, nor StudentChargePayment or StudentBillingReceipt. Payment also lacked overtimeHours and overtimeRate. The runtime Prisma client expected these structures, so the billing GET failed before the form could load.

## Repair

The additive SQL is maintained in [20261122080000_repair_missing_student_billing](../prisma/migrations/20261122080000_repair_missing_student_billing/migration.sql).

It restores the current billing definitions represented by the existing services, reconciliation, receipt, category and custom-kind migrations:

- StudentServiceAssignment, including service discounts and custom charge kinds.
- StudentCharge, including nonnegative balance constraints and custom kinds.
- StudentChargePayment, including paidAt and paymentMethod.
- StudentBillingReceipt, including allocations and paymentMethod.
- StudentChargeCategory.
- The composite Student identity index used by school-scoped foreign keys.
- Missing Payment overtime columns, and supporting Institution columns only if absent.

The repair runs transactionally with bounded lock/statement timeouts. New billing tables have RLS enabled and direct PUBLIC/anon/authenticated grants revoked. Existing students, family links, tuition prices and payment records are not backfilled or rewritten. No charges or receipts are generated by the repair.

The SQL uses IF NOT EXISTS for repeatable creation, not to reconcile arbitrarily incompatible existing tables. Review an environment's actual definitions before reuse. Do not run a reset, seed or blanket schema push.

## Production evidence

The target dashboard showed the main PRODUCTION branch. Before the repair, metadata listed none of the five billing tables. Existing records were 498 students, 378 parents and zero payments. The repair returned success.

A subsequent read-only query confirmed:

- All five tables exist with RLS enabled.
- Both overtime columns, receipt paymentMethod and charge-payment paidAt exist.
- Student and parent totals match the pre-repair baseline.
- Payment count and total are unchanged.
- A fingerprint of level tuition prices matches the pre-repair baseline.
- No charges or receipts were created.
- No direct PUBLIC/anon/authenticated grants exist on the billing tables.

This was applied through SQL Editor; Prisma migration-history entries were not marked applied or reconciled. The original older migrations may contain statements that now overlap this repair. Inspect actual schema and history before a future migrate deploy; do not blindly rerun older SQL or mark an entire history applied.

## Application change and verification limit

The admin student-billing API now returns HTTP 503 with a clear French message and BILLING_SCHEMA_REQUIRED for Prisma missing-table/missing-column errors. It logs only the error code for these cases rather than returning the raw Prisma query error to the administrator. Normal business-validation responses remain unchanged.

The schema repair is effective independently of deploying that error-message change. Static TypeScript and targeted lint checks were used. No test suite or live collection, receipt generation, provider call or payment simulation was performed, following the user's preference to test themselves. Refresh/reopen the payment form for user acceptance.

Unrelated parent-access schema gaps are separate and were not repaired by this billing operation.
